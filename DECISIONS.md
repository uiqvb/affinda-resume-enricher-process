## Foundational decisions (Sprint-2 planning, locked 2026-11-13)

These are the "D1–D9" locked decisions that set the whole shape of v1.

- **D1 — Modules.** Four feature modules, each its own self-contained blob. v1 ships **Skill,
  Education, Certification**; **Employment-Date** is module 4, a fast-follow that needs its own
  taxonomy + 100 resumes first. Education and certification share one invisible internal status
  engine.
- **D2 — Never touch the original.** Our labels live in a **separate `resumeGuard` block**;
  Affinda's original `data` is copied byte-for-byte and never mutated (enforced by an assert).
  Annotations reference the original by index. Affinda's own input keys keep their real names.
- **D3 — Evidence.** Every annotation carries proof = **a quoted snippet + rawText character
  offsets** (so a human can see exactly where we got it).
- **D4 — Status vocabularies (the field is named `status`, not `label`):**
  - skill: `strong / intermediate / basic / learning / lapsed / no_experience / plain`
  - education: `completed / in_progress / expected / incomplete / deferred / not_awarded / unknown`
  - cert: `active / expired / revoked / suspended / pending / unknown`
- **D5 — Detection method.** Entity-anchored 3 steps (locate entity in rawText → read the
  surrounding clause → match a cue regex) + an adjacency precision rule. **When unsure → stay
  safe (`plain`/`unknown`)**; that "unsure" pile is the future-LLM target.
- **D6 — Grading.** Acceptance runs on a **NEW blind held-out batch** generated by a separate
  agent told only *what* to test (the 3 status types + List-B defect patterns), never *how* we
  detect them. Compare our status to ground truth; count right/missed/wrong + controls +
  distractor traps. **Bar = measure first, set the pass line after seeing real numbers.** The
  original 300 scored resumes stay only as a dev sanity-check.
- **D7 — Deliverable.** All four interfaces over 3 iterations: iter 1 = **library + CLI**;
  iter 2 = **+ web API**; iter 3 = **+ dockerized API**. A demo script ships from iter 1.
- **D8 — Tech stack.** Python 3.11+, the **`regex`** module (fuzzy matching) for the brain,
  **typer** CLI, **FastAPI + uvicorn** API, **Docker + compose**, pytest. No spaCy, no LLM in v1.
- **D9 — List-B handling.** v1 includes BOTH (1) a **date caveat** (warn when an
  incomplete/withdrawn/expected degree still carries a graduation-looking end date) and (2) a
  **missing-entity flag** (scan rawText for skills/credentials absent from Affinda output → flag
  as possibly-dropped; uses a guarded list to limit false alarms).

- **Architecture.** Project structure = **feature-sliced modular monolith**.
  - *Options considered:* (a) **three zones**, (b) **layered/clean**, (c) **feature-sliced
    modular monolith** ✅. Chosen after an independent zero-context agent review confirmed it
    (not sycophancy). Four tiers, one-way deps only: `delivery → app → modules → shared`.
    Boundary enforced by one `tests/test_boundaries.py` import-direction test — no base classes,
    no plugin framework. Shared folder named `shared/` (you chose this over `kernel/`).

## Day-3 design walkthrough decisions (2026-11-14)

Walking `DESIGN.md` piece by piece and locking the fine-grained calls.

- **Piece 4 — Locator, text cleaning → Option B.** When finding an entity in rawText, clean the
  text **fully** (lowercase + collapse whitespace + strip punctuation) so messy cases like
  "S Q L", line-break splits and stray punctuation still match. Because full cleaning changes
  length, keep a **per-character index map** from the cleaned position back to the original
  position, so evidence highlights/spans stay exact.
  - *Options considered:*
    - **Option A — gentle clean (length-preserving):** only lowercase, never delete/squish, so
      offsets line up automatically. Simpler, less code, **but** can miss matches in messy text.
    - **Option B — full clean + index map** ✅ (chosen): squish everything for maximum matches,
      plus a cheat-sheet map to translate positions back so highlights stay exact.
  - *Why B:* catches more matches in messy real-world text; the index map keeps the "exact proof
    location" promise honest. Accepted the extra bit of code.

- **Piece 5 — Rulebook, fuzzy matching → killers only.** Typo-tolerant fuzzy matching is applied
  **only to the decisive "killer" cues** that flip a claim good→bad (skill `no_experience`,
  education `incomplete`/`not_awarded`, cert `expired`/`revoked`/`suspended`). Soft/positive cues
  (basic, strong, learning, completed, active, …) are matched **exactly**.
  - *Options considered:* (a) **fuzzy everywhere** — most forgiving but invites false alarms;
    (b) **fuzzy on killers only** ✅ — tolerance where it pays off, exact elsewhere.
  - *Why:* fuzzing the soft cues invites false alarms; the killers are where tolerance pays off.

- **Piece 5 — "expected" needs a future year.** The education `expected` status only fires when
  the clause also contains a year **greater than the current year**. "expected" alone, or with a
  past year, does not count.

- **Piece 6 — Precision guard window → 6 tokens.** A cue word binds to a skill only if it sits
  within **≤ 6 tokens** of that skill (plus same-clause and no-wall-between). Chosen as a sane
  starting point, to be tuned against the test batch.

- **Piece 6 — Wall words (scope breakers) → research-backed list.** A "wall" between a cue and a
  skill blocks the cue from reaching that skill. Grounded in discourse-connective research:
  - **Hard punctuation walls:** `;` `.` newline `|` `—` `–` `/` `•` and bullet-dashes.
  - **Contrast/concession walls:** but, yet, however, though, although, whereas, while,
    nevertheless, nonetheless, except, aside from, apart from, other than, instead, on the other
    hand.
  - **NOT walls (keep one scope):** and, or, nor, as well as, plus.
  - **Comma = conditional wall:** a wall only when a cue word follows it (", but no experience"),
    not when it just separates a plain skill list ("Python, Java, SQL").
    - *Options considered for the comma:* (a) **every comma = hard wall** — risks cutting plain
      skill lists; (b) **conditional comma** ✅ — wall only when a cue follows it.
  - *Window options considered:* I proposed **6 tokens** as a sane start (tight enough to stop
    leaks, loose enough to catch real cases); accepted, to be tuned against the test batch.

- **Piece 7 — Report scope → PROBLEM CATCHER (only flag problems).** ⚠️ **SUPERSEDED on
  2026-11-14 — see "Report scope REVERSED → FULL ENRICHER" below.** (Original call:) emit an
  annotation only for a status that signals a problem; confirmed-good / neutral / unknown stay
  silent.
  - *Options considered:* (a) **only flag problems** ✅; (b) **report everything** (good news
    too) — fuller picture but noisy and more chances to mislabel; (c) problems-by-default +
    verbose switch (deferred — easy future add).
  - *Why:* "better to flag what is potentially wrong than to stamp 'good' on everything and risk
    being wrong on a clean entry." Keeps the tool sharp, safe, and easy to test.
  - Encoded in `DESIGN.md §2d` as `PROBLEM_STATUSES`; applied in §6 (skill) and §7 (status
    engine).

- **Piece 7 — Date-only degree → `unknown` / silent.** A degree showing only a graduation date
  and no status words is labelled `unknown` (and so stays silent), never assumed `completed`.
  - *Options considered:* (a) **leave 'unknown'/silent** ✅; (b) assume `completed` — matches
    most real resumes but could mislabel a withdrawn degree that still carries a year.
  - Fixed the stale §7 fallback that previously returned `completed` on a bare past date.

- **Report scope REVERSED → FULL ENRICHER (decided 2026-11-14, supersedes the problem-catcher
  call above).** We record a status for **EVERY** item (skill/degree/cert), not just the bad
  ones — a **complete mirror** of Affinda's list with added metadata. Each enrichment carries a
  **`severity`** tag: `warning` (worth a recruiter's attention) or `info` (fine / neutral
  context). Items where we find no signal are still listed (`plain` for skills, `unknown` for
  edu/cert — both `info`).
  - *Why the reversal:* revisited List A (the product) — item 3 is the **whole** claim-strength
    range ("expert … exposure … no experience"), so positives were always in scope. And thinking
    as a SEEK-type customer: a data platform prefers **complete, predictable** data and filters
    it itself — "easier to filter out what you don't want than to recover what you never got."
    `plain`/`strong` vs a dropped row is itself useful signal (supported claim vs bare mention).
    A problem-*catcher* decides for the customer; an **enricher** hands over everything + a
    severity tag and lets them choose.
  - *Mechanism change:* the old "problem filter" (`PROBLEM_STATUSES`) became a **severity stamp**
    (`STATUS_SEVERITY` in `models.py`) — one table listing every allowed status and its
    warning/info tag; its keys double as the "allowed statuses" menu (a typo → `severity_of()`
    fails loudly, which also settles the earlier allowed-statuses question). `Enrichment` gained
    a `severity` field.
  - *Still true:* date-only degree → `unknown` (now emitted as `info`, still never assumed
    `completed`).

- **List B (parser bugs) handling — confirmed 2026-11-14.** We cannot fix Affinda's parser (it's
  a closed third-party model; we only see its output) and we never edit its data (contract). But
  our enricher **flags** the ones it safely can: #1 dropped skills + #2 missing "Bar admission"
  → the missing-entity check; #3 "withdrawn <year>" shown as a grad date → a date caveat. #4
  "Juris Doctor mis-tagged as master's" is NOT auto-flagged (re-classifying a degree type is
  error-prone) — just reported to Affinda.

## Eval decisions

- **Real-resume precision slice → ADDED (decided 2026-11-14).** A *second* eval set alongside
  the D6 blind batch: a slice of **real resumes** (e.g. the Kaggle LiveCareer set or a research
  corpus) used **only to measure false alarms** — since real resumes almost never contain our
  target flaws, any flag we raise is a suspect to inspect. Recall stays measured on the generated
  blind batch. Requires running the real resumes through Affinda first.
  - *Options considered:* (a) generated blind batch only (original D6) — clean answer key but no
    real-world noise test; (b) **add a real-resume precision slice** ✅ — measures false alarms
    on messy real text, no answer key needed.

## Build-sprint decisions (2026-11-14 — "finish end to end, I'll audit next")

These were decided *during implementation* to finish a coherent v1. They are marked so
the audit can accept, change, or reverse each one.

- **Evidence points at the CUE, not the entity (decided 2026-11-14).** `evidence.text` and
  `evidence.rawTextSpan` must describe the SAME thing. When a cue is found, both describe the
  cue ("no experience" → its span); when no cue is found (`plain`/`unknown`), both describe the
  item itself. Enforced in one place: `models.build_evidence()`.
  - *Why:* the minimal version set text = cue but span = entity location — a real inconsistency
    the user flagged. The proof of a warning IS the cue, so the highlight should point there.
  - *Options considered:* (a) span = entity location (what Affinda already gives — redundant);
    (b) **span = cue location** ✅ (the actual proof); (c) carry BOTH an entity span and a cue
    span — rejected for v1 as extra shape the customer can reconstruct from `entryIndex`.
  - *Mechanism:* `locate()` now returns `(clause, clauseStart, span)`; classifiers return the
    cue's position inside the clause; `build_evidence` adds `clauseStart + position` to get the
    cue's spot in the whole resume.

- **Skill precision guard = WALL split (decided 2026-11-14).** Implemented the DESIGN §6 wall
  idea: cut the sentence at punctuation (`, ; : |`) AND joining words (and/but/however/whereas/
  while/though/also/plus), then read only the piece containing the skill.
  - *Options considered:* (a) read the whole sentence — rejected, cues leak between skills;
    (b) comma/semicolon split only (the minimal version) — worked on the sample but missed
    word-walls like "but"; (c) **punctuation + wall-word split** ✅; (d) full ±6-token window
    counter (DESIGN §6 original) — deferred as heavier than needed for v1 accuracy.
  - *Note:* the earlier "≤6 tokens" window decision is effectively superseded by the wall split
    for v1. Flagged for the audit to confirm.

- **Tests use stdlib `unittest`, not pytest (decided 2026-11-14).** 34 checks, runnable with
  `python -m unittest discover -s tests`, no third-party install.
  - *Why:* pytest isn't installed in this env; D8 named pytest but a zero-dependency net runs
    anywhere and reads the same. *Options:* (a) pytest (D8's choice, needs install); (b)
    **stdlib unittest** ✅; audit can switch to pytest later with no logic change.

- **List B kept minimal for v1 (decided 2026-11-14).** The missing-entity signal is surfaced as
  `confidence:"low"` when an item can't be located in rawText; no separate date-caveat /
  rawText-scan subsystem was built yet (D9 / the 2026-11-14 List-B decision remain the target).
  - *Why:* kept the audit surface tight — the three List-A enrichments are the product; List-B
    is a fast-follow. *Options:* (a) build D9's full date-caveat + missing-entity scan now;
    (b) **defer, lean on `confidence:low` for v1** ✅. Flagged openly for the audit.

- **Fuzzy matching deferred (reaffirmed 2026-11-14).** v1 uses stdlib `re` with exact cue
  matching; the `regex` module `{e<=1}` fuzzy layer (D8, Piece 5) is not wired in yet. Documented
  as a known limitation in every rules doc + docs/README.md.

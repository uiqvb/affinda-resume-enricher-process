What I made, and how I got there.

I'm Manit Khera, a third-year Software Engineering student at Deakin. Over four days I built a tool on top of your Resume Parser, and I recorded a short video after each work block.

This page goes through it day by day. The tool does not change Affinda's output. It reads the parsed JSON and writes a separate set of notes, or enrichments, beside it.

The reflection videos under each day started as something just for me. I could have built the tool without them, but recording one after each work block left a trail of how my thinking changed as I went, so I've linked them in case you want to see it.

I try to keep things simple.

Day 1 · Ideation
12 November 2026

Finding the gap

I started by going through what Affinda builds, before writing any code. I looked at the whole range, including the document parser and the tool that compares two documents, and for each one I thought about what I could add on top of it. A few seemed workable, so I kept the document parser and the compare tool as backups. In the end I chose the Resume Parser and focused there.

I began by testing where it might fail. I used Claude to generate a set of fake resumes and ran them through the parser. Some of them had white, hidden text. A few had short instructions planted inside them, so I could see whether the parser would act on them. It did not. The hidden text showed up in the raw text but never changed a field, and the planted instructions were read as plain text, not followed. The main reading was accurate: names, phone numbers, titles and dates were almost all correct, and a scanned, image-only PDF still came back right.

The gap was somewhere else. Not in what the parser reads, but in what it records about each item. Whether a skill is claimed or denied. Whether a degree was finished. Whether a certificate is still valid. That part was getting lost.

To avoid reading too much into one result, I tried to disprove each finding rather than confirm it. I ran 183 fake resumes across four rounds, and retested every finding before I kept it. One thing that looked like a problem came back correct 15 out of 15, so I dropped it. I also recorded one issue as a bug, then found in Affinda's docs that it was intended behaviour, so I removed it. The aim was to catch my own mistakes as well as the parser's.

What was left was a single pattern that kept repeating. The parser keeps the item, but drops the word next to it that changes what it means.

Day 2 · Planning
13 November 2026

Confirming it, and choosing the scope

I cut the day to four hours, because six had been too long to stay focused.

I made 300 more fake resumes, each one differing from the last by a single line, so I could test one variable at a time. The result held. In every case I checked, the status field was not there. Not wrong, just missing.

Denied skills
"no experience with SQL" still comes back as a skill.
9 of 10
Unfinished degrees
A dropped-out degree looks finished.
20 of 22
Expired certs
An expired cert reads as valid.
33 of 36

I checked this against Affinda's own documentation. These three fields are not in the current schema: there is no skill strength, no completion status for a degree, and no validity status for a certificate. So the tool adds information that is not there, rather than repeating something that is.

I kept two separate lists. List A was the missing information the tool would add, which became the product. List B was a few parser bugs I came across and noted for reference, not something to build on, since the parser is not mine to change.

The main decision was what to leave out. I considered adding a small AI model to handle wording the rules could not, and I decided against it for now. When the tool is not sure, it marks the item unknown and leaves the judgement to a person. A clear flag is easier to filter than missing information is to recover.

Day 3 · Execution
14 November 2026

Building it

My plan was to go through it file by file, agreeing on each naming convention with Claude Code as I went. That turned into a lot of back-and-forth over names and took too long, so I changed approach. I let it build the engine in one pass, then read through the whole flow from the start and fixed the parts that matter to a person, mostly the naming and structure. A model will not tell you a name reads poorly, so that part needs a person.

I also compared the finished code against my day one and day two notes, to check it still did what I had planned. In a couple of places it did not, so I corrected those.

The engine is small on purpose. Every skill, degree and certificate goes through three steps. Find it in the text. Read what is around it. Tag it. Each tag answers three questions.

What does it say?
The word in the text, like "no experience" or "expired".
Needs a look?
Yes or no, from a fixed list.
Did we find it?
High if we saw it in the text, low if not.

The main rule

If it is not sure, it stays silent. It would rather miss a real problem than flag a genuine candidate by mistake. A missed flag is low cost; a wrong one is not.

I found two bugs by checking the output rather than guessing. The locator was treating a dash as the end of a line, so it cut off words like "expired" in "CISSP, expired 2022". Fixing that raised the degree and certificate results from about 30 percent to the numbers below. Separately, my test code was comparing "AWS" against Affinda's renamed "Amazon Web Services" and missing the match, until I changed it to use the original text.

Day 4 · Testing
15 November 2026

Testing it

First I added the interfaces: a command line, a small web endpoint, and Docker. I looked at load testing and decided it was not the right measure here. The tool is a stateless function with no database, so single-run speed matters more than scaling. It processes about one resume per millisecond, roughly a thousand a second on one core.

Then the main test. Out of the real problems in the set, how many did it catch?

No clean resumes wrongly flagged, across all 300. About one resume per millisecond.

A test built on my own data is a limited test, so I ran two harder ones. The results are below, including the places where it did poorly.

Wording it had not seen

It was 90 percent correct on wording it already covers, and 0 percent on new wording. The rules do not generalise to phrasing they have not seen. When it misses, it stays silent, so there were no false alarms.

18 real resumes

No false alarms on degrees or certificates. The mild "basic" tag fired 23 times on stray words like "Basic First Aid". I had earlier said it never flags a clean item; the real resumes showed that was not correct, so I changed the claim.

What I have not tested yet

I have tested the problem thoroughly, across hundreds of resumes. I have not yet measured how well the fix performs on new, unseen data. Those are two separate things, and that measurement is the next step.

Near the end of the day I renamed a field I could no longer follow, from "severity" to "needs review", and changed its values from "high, warning, info" to "yes or no". It is a small change, but it is the kind of thing I check for.

Day 5 · Handover
17 November 2026

Handing it over

I was off sick on the 16th, so the handover moved to the next day. The four days of work left me with a working tool and a large, unstructured set of notes. I split them into two repositories: one with the tool you can run, and one that keeps the tests, the lists, and the transcripts of these videos.

The rest of the day went on getting it ready to send: recording and editing the intro video, putting this page together, and checking every number and link before it went off for review.

You can run it yourself. Install it, run the sample, run the 34 tests, and run the evaluation. Every number on this page is regenerated from the data.

Where it goes next

  • Add a small AI step, used only on the items the rules mark unknown.
  • Narrow the "basic" tag so it only counts when the word sits on the skill itself.
  • Add a check for a missing end date on a current job.
  • Measure the fix on new, unseen resumes.

If you have time to look, I would appreciate your feedback on it.
